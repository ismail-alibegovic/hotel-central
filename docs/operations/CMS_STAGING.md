# Hosted CMS demo — Supabase PostgreSQL + Vercel runbook

Status: the CMS runs on **PostgreSQL** (`@payloadcms/db-postgres`, committed migrations in `src/migrations`). The hosted demo uses a Supabase project (Free plan), Vercel Blob for media and a separate, protected Vercel project. Nothing here touches the public demo project (`hotel-central`) or the hotel's own website.

## 1. Target architecture
```
Browser ──► Vercel project "hotel-central-cms-demo" (one Next.js 16 app: public site + /admin + /api)
                │  Local API (in-process)                     │ client upload (staff only)
                ▼                                             ▼
   Supabase PostgreSQL (DATABASE_URL, pooler)         Vercel Blob (BLOB_READ_WRITE_TOKEN)
```
- Same app serves the static public pages (prerendered, regenerated by `revalidatePath` on publish) and the CMS.
- Serverless: no local disk writes when Blob is configured; pool of 3 connections per instance, 4 s connect / 15 s query timeouts so pages fall back to static content when the database is unreachable; media uploads go browser → Blob (`clientUploads`, staff only) because Vercel Functions reject request bodies over 4.5 MB.
- **Connection string: use the Supabase *pooler* string** (Project → Connect → Transaction pooler, port 6543, host `…pooler.supabase.com`). The direct `db.<ref>.supabase.co` host is IPv6-only and cannot be reached from Vercel (`cms:preflight` rejects it). TLS is always on for non-local hosts; the Supabase CA is not in Node's trust store, so the connection is encrypted but the server certificate is not verified (documented trade-off in `src/cms/db.ts`).
- Schema changes are **migrations**, never auto-push: `npm run cms:migrate` applies pending ones (idempotent); `npm run cms:seed` runs them first, then seeds.

| --- | :-: | :-: | --- |

| `ALLOW_FIRST_REGISTER` | **unset** | no | Keeps "register the first user" closed. |

`tests/int/env.int.spec.ts` fails if a `NEXT_PUBLIC_*` name other than the two public URLs appears in `src/`, if a client file reads a secret, or if credential-shaped strings are committed; `npm run test:cms-e2e` also scans the built client bundle for the run's real secrets and DB host. `npm run cms:preflight -- staging` checks a hosted environment's variables without printing values.

## 3. Provisioning runbook
1. **Supabase** (Free): create project `hotel-central-cms` in an EU region (done: eu-central-1). Set/reset the database password in *Project Settings → Database* (the API that created the project does not return it) and copy the **pooler** connection string with that password. Do not paste it into chat or Git.
2. **Vercel project** `hotel-central-cms-demo` from the same GitHub repository, framework Next.js, Node 24.x, **Build Command** `npm run build`, with an *Ignored Build Step* so that only the `staging` branch is built. The build does **not** migrate or seed: the database is changed deliberately, never as a side effect of a deployment (see §3a).
   - **How the hosted demo actually runs today:** the *Production Branch* in Vercel is still `main` (it can only be changed in the Vercel dashboard); the staging site is a **production-target deployment of the `staging` branch created by hand** (Vercel API/CLI with `ref: staging` and the exact commit), which is what the stable address `hotel-central-cms-demo.vercel.app` points to. A plain `git push` to `staging` therefore creates a *preview* deployment (not the stable address) — cancel it or use it for checking. Setting *Production Branch* = `staging` in the dashboard would make a push deploy to the stable address; this has not been done.
   - Deployment Protection → **Vercel Authentication, All Deployments** (must stay on; never share bypass links with people who should not see the demo).
   - Env vars above scoped to **Production only** (preview deployments of other branches stay static).
3. **Blob store** (public access; the adapter supports public stores only), connected to the project (injects `BLOB_READ_WRITE_TOKEN`).
4. First setup: run `npm run cms:migrate` and `npm run cms:seed` once with `SEED_ADMIN_EMAIL` + `SEED_ADMIN_PASSWORD` set (from a machine that can reach the pooler; the hosted demo was seeded from a Vercel Sandbox in `fra1`, because a build in `iad1` was too slow for the many round trips). Afterwards **delete both variables in the Vercel dashboard** (setting them to an empty value is not the same as deleting them; on the hosted demo they were blanked through the API and still need deleting by hand). The seed never overwrites existing content, so running it again is safe.
5. Verify: `/admin` shows the Payload login behind the Vercel login wall; log in; walk through §7.

## 3a. Changing the hosted demo (deploys and migrations)
**A normal code change** (no database change): merge the pull request into `main`; fast-forward `staging` to that commit (`git push origin <commit>:refs/heads/staging`, fast-forward only); create the production-target deployment of that exact commit from `staging`; check `/admin` signed in (the acceptance checklist in `docs/admin-ux/STAGING_ACCEPTANCE.md`). Rolling back = promote the previous deployment in Vercel.

**A change that needs a migration** (new field or table): the build does not apply it, so the order matters because code that reads a new column must not run before the column exists.
1. `pg_dump` the hosted database first (see §4) and keep the file.
2. Generate and **review** the migration SQL (`npm run cms:migrate -- create`); try it on a restored copy: `npm run cms:rehearse` (§4) takes the backup, restores it into a scratch database, applies the migration, rolls it back and applies it again, and reports every check.
3. Apply it to the hosted database from a machine that can reach the **pooler** string: `DATABASE_URL=<pooler> npm run cms:migrate` (idempotent; it applies only pending migrations).
4. Deploy the code.
**Undoing a migration:** redeploy the previous code (the new tables are then simply unused). Only if the schema itself must go back: `DATABASE_URL=<pooler> npm run cms:migrate -- down --yes` rolls back the last batch (drops what it created, including anything staff entered there), after a fresh `pg_dump`.
Pure wording, label, tab or component changes in the admin do **not** change the database (the generated migration is empty; the CI check `cms:migrate -- create` confirms it).

## 4. Backup and restore
The hosted database is **PostgreSQL 17** (Supabase project `hotel-central-cms`, eu-central-1). Details, evidence and the exact approval sequence: `docs/operations/HOSTED_MIGRATION_READINESS.md`.

| What | How | Tested |
| --- | --- | --- |
| Database | `npm run cms:rehearse` (below) takes the backup **and** proves it restores. By hand: `pg_dump --format=custom --schema=public --no-owner --no-privileges --file=backup.dump` with the **session-mode** connection (see below) | backup, isolated restore, migration up/down/up and the CMS booting on the copy: **tested on a PostgreSQL 17 replica of the hosted schema (26 checks)**; not yet run against the hosted database itself (needs the owner's connection string) |
| Media | `npm run cms:backup-media <dir>` (downloads every file referenced by the Media collection) | local-disk path tested. **The Blob download path has not been exercised on a real store** (the demo library was empty when this was written): run it once against a store that holds a few photos before relying on it |
| Code/config | Git (`main`, `staging`) | continuous |
| Secrets | password manager owned by the hotel/agency; never in Git | n/a |

**Three things that are easy to get wrong (all found while rehearsing, none visible in the tests that use PostgreSQL 16):**
1. **Use PostgreSQL 17 tools.** A 16 `pg_dump` refuses a 17 server ("server version mismatch") and a 16 `pg_restore` cannot read a 17 archive ("unsupported version (1.16) in file header"). Install `postgresql-client-17` (PGDG apt repository), or run the tools from the `postgres:17` Docker image, or use the unpacked packages as in the readiness document, and point `PG_BIN` at them. The restore target must also be 17.
2. **Use a session connection for `pg_dump`, not `DATABASE_URL`.** `DATABASE_URL` is the transaction pooler (port 6543), which cannot run `pg_dump`. Use the *session pooler* string (Project → Connect → Session pooler, port 5432, user `postgres.<project ref>`) or the direct connection when the machine has IPv6.
3. **Dump `--schema=public` only** (every CMS table lives there; the other schemas belong to Supabase), and restore from the archive's table of contents **without** its `SCHEMA public` entry (`pg_restore --list backup.dump | grep -v ' SCHEMA - public ' > restore.list`, then `pg_restore --use-list=restore.list …`): the archive's own `CREATE SCHEMA public` fails on every database that already has one, including a new Supabase project.

**Backup + isolated restore + migration rehearsal (repeatable, never writes to the source):**
```bash
export PG_BIN=/usr/lib/postgresql/17/bin                       # PostgreSQL 17 client tools
export SOURCE_DATABASE_URL='<session-mode connection string>'  # read only; from the password manager, never pasted into chat or Git
export RESTORE_ADMIN_URL='postgres://postgres@127.0.0.1:5432/postgres'   # a LOCAL PostgreSQL 17 server; the script creates and drops one scratch database
npm run cms:rehearse                                            # backup file + report go to ./backups (ignored by git)
```
It checks that the backup is readable and complete (sha256, 188 of 188 tables), that the restored copy has the same tables, rows (count **and** checksum of every table) and schema as the source, that the pending migrations apply to the copy without changing anything that existed, that `cms:migrate -- down --yes` returns the copy exactly to the restored state and the migration applies again, that `cms:seed` afterwards changes only the new tables, and that the CMS boots on the copy and reads pages, rooms, users and every global. It refuses a restore target that is not local, a transaction-pooler source, tools older than the server, and it **fails loudly if the source changed while it was being backed up** (rerun when nobody is editing). Passwords never appear in its output or report.

**Older drill:** `HC_TEST_PG_URL=postgres://… npm run cms:restore-drill` (CI, PostgreSQL 16) writes users, pages and media into a throw-away database, dumps it, drops the source, restores, and verifies the admin logs in with the original password, both locales and the draft are intact and the media file exists. It proves the login/password-hash round trip, which the rehearsal does not (it never knows a password).

**Real restore (Supabase):** 1) unset `CMS_ENABLED` (public pages keep serving static content); 2) create a **new** Supabase project (or empty database) of the same major version; 3) run `pg_restore` with the table-of-contents trick above into it, from a machine that can reach its session pooler or direct host; 4) point `DATABASE_URL` (transaction pooler) at it and redeploy; 5) verify login + a published page; 6) re-enable. Supabase Free does not include backups you can rely on — treat your own `pg_dump` as the only backup and check Supabase's current plan page before depending on anything else. **No scheduled backup exists yet** (see the readiness document).

## 5. Security posture (summary; details in PAYLOAD_POC.md and DEPENDENCY_AUDIT.md)
Roles enforced server-side (not only in the UI); editors cannot publish, unpublish, restore, delete, change slugs/booking mapping, or manage users; drafts invisible to anonymous reads on every REST path tested (filters, sorts, versions, counts, search); no user/credential enumeration; GraphQL disabled; CSRF origin lock + CORS allow-list; `HttpOnly`/`Secure`/`SameSite=Lax` session cookie, 2 h sessions, lockout after 5 failures; admin/API responses noindex + `nosniff` + `X-Frame-Options: SAMEORIGIN`; uploads: images only, content-sniffed, ≤ 8 MB, alt text required, SVG rejected.
Known gaps: no rate limiting on login beyond per-account lockout (Vercel Firewall rules are available on all plans — add one for `/api/users/login` before production); password reset e-mail needs a real provider; no MFA (Payload supports it via plugins — evaluate for admin accounts).

## 7. Staging acceptance checklist (after provisioning)
> A step-by-step version for a person with no technical background (sign in, change a room, photos, publish, editor role, phone) is `docs/admin-ux/STAGING_ACCEPTANCE.md`. The numbered list below is the technical checklist.

1. `/admin` login as admin; create an editor; log in as editor in another browser.
2. Editor edits About (EN) → **Save Draft**; confirm no Publish button; confirm the public page is unchanged; use **Live Preview**.
3. Admin publishes; public EN page updates immediately; BS page unchanged; repeat for BS.
4. Same for Junior Suite; booking button still points to `roomtypeunkid=18019000000000000010`.
5. Upload an image (≤ 8 MB, with alt text); confirm it is served from `*.blob.vercel-storage.com`; try an SVG (must be refused).
6. Restart/redeploy; confirm content and media persist.
7. Take a `pg_dump`; run the restore procedure into a scratch database; verify.
8. Confirm `x-robots-tag: noindex` on `/`, `/admin`, `/api/*`; confirm staging URLs return the Vercel login wall when signed out.
9. Rotate `PAYLOAD_SECRET` once to prove the procedure.
