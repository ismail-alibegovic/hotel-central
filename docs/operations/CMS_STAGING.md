# Hosted CMS demo — Supabase PostgreSQL + Vercel runbook

Status: the CMS runs on **PostgreSQL** (`@payloadcms/db-postgres`, committed migrations in `src/migrations`). The hosted demo uses a Supabase project (Free plan), Vercel Blob for media and a separate, protected Vercel project. Nothing here touches the public demo project (`hotel-central`) or the hotel's own website.

## 1. Target architecture
```
Browser ──► Vercel project "hotel-central-cms-demo" (one Next.js 16 app: public site + /admin + /api)
                │  Local API (in-process)                     │ client upload (staff only)
                ▼                                             ▼
   Supabase PostgreSQL (DATABASE_URL, pooler)         Vercel Blob (BLOB_READ_WRITE_TOKEN)
```
- Same app serves the static public pages (prerendered, regenerated by `revalidatePath` on publish) and the CMS.
- Serverless: no local disk writes when Blob is configured; pool of 3 connections per instance, 4 s connect / 15 s query timeouts so pages fall back to static content when the database is unreachable; media uploads go browser → Blob (`clientUploads`, staff only) because Vercel Functions reject request bodies over 4.5 MB.
- **Connection string: use the Supabase *pooler* string** (Project → Connect → Transaction pooler, port 6543, host `…pooler.supabase.com`). The direct `db.<ref>.supabase.co` host is IPv6-only and cannot be reached from Vercel (`cms:preflight` rejects it). TLS is always on for non-local hosts; the Supabase CA is not in Node's trust store, so the connection is encrypted but the server certificate is not verified (documented trade-off in `src/cms/db.ts`).
- Schema changes are **migrations**, never auto-push: `npm run cms:migrate` applies pending ones (idempotent); `npm run cms:seed` runs them first, then seeds.

## 2. Environment variables
| Variable | Demo project | Secret? | Notes |
| --- | :-: | :-: | --- |
| `CMS_ENABLED` | `true` | no | Must exist in **Build and Runtime**. Unset ⇒ static site, `/admin` and `/api/*` (except `/api/contact`) answer 404. |
| `DATABASE_URL` | Supabase pooler string | **yes** | Contains the database password. Mark *Sensitive*. |
| `PAYLOAD_SECRET` | ≥ 32 random chars | **yes** | Different per environment. Rotating it logs everyone out. |
| `NEXT_PUBLIC_SERVER_URL` | `https://<stable demo origin>` | no | CORS/CSRF allow-list and Live Preview; must equal the origin editors use. |
| `BLOB_READ_WRITE_TOKEN` | injected when the Blob store is connected | **yes** | `vercel_blob_rw_<store>_<random>`. |
| `SEED_ADMIN_EMAIL`, `SEED_ADMIN_PASSWORD` | first deploy only | **yes** | Creates the first administrator; **delete both afterwards**. Never reuse a personal password. |
| `NEXT_PUBLIC_SITE_URL` | **unset** | no | Unset keeps the site `noindex`. |
| `ALLOW_FIRST_REGISTER` | **unset** | no | Keeps "register the first user" closed. |
| `CMS_ALLOW_SAMPLE_PUBLISH` | **unset** | no | Keeps DEMO / SAMPLE sections unpublishable. |
| `MEDIA_DIR` | — | no | Local disk media for dev/tests only. |

`tests/int/env.int.spec.ts` fails if a `NEXT_PUBLIC_*` name other than the two public URLs appears in `src/`, if a client file reads a secret, or if credential-shaped strings are committed; `npm run test:cms-e2e` also scans the built client bundle for the run's real secrets and DB host. `npm run cms:preflight -- staging` checks a hosted environment's variables without printing values.

## 3. Provisioning runbook
1. **Supabase** (Free): create project `hotel-central-cms` in an EU region (done: eu-central-1). Set/reset the database password in *Project Settings → Database* (the API that created the project does not return it) and copy the **pooler** connection string with that password. Do not paste it into chat or Git.
2. **Vercel project** `hotel-central-cms-demo` from the same GitHub repository, *Production Branch* = `staging` (a branch created from `main`), framework Next.js, Node 24.x, **Build Command** `npm run cms:migrate && npm run cms:seed && npm run build` (migrate + seed are idempotent and run inside the build because Postgres is only reachable from Vercel, not from a developer's sandbox).
   - Deployment Protection → **Vercel Authentication, All Deployments**.
   - Env vars above scoped to **Production only** (preview deployments of other branches stay static).
3. **Blob store** (public access; the adapter supports public stores only), connected to the project (injects `BLOB_READ_WRITE_TOKEN`).
4. First deploy with `SEED_ADMIN_EMAIL` + `SEED_ADMIN_PASSWORD` set; afterwards **remove both** and redeploy (the seed never overwrites existing content, so redeploys are safe).
5. Verify: `/admin` shows the Payload login behind the Vercel login wall; log in; walk through §7.

## 4. Backup and restore
| What | How | Tested |
| --- | --- | --- |
| Database | `pg_dump --format=custom --no-owner --no-privileges --file=backup.dump "$DATABASE_URL"` before every release/migration; restore with `pg_restore --no-owner --no-privileges --dbname=<new database URL> backup.dump` | dump + restore **tested** by `npm run cms:restore-drill` (local PostgreSQL; CI runs it on every PR) |
| Media | `npm run cms:backup-media <dir>` (downloads every file referenced by the Media collection) | local-disk path tested; Blob download path tested on the demo store (see the acceptance report) |
| Code/config | Git (`main`, `staging`) | continuous |
| Secrets | password manager owned by the hotel/agency; never in Git | n/a |

**Drill (repeatable):** `HC_TEST_PG_URL=postgres://… npm run cms:restore-drill` (needs `pg_dump`/`pg_restore`) writes users, pages (both locales + a pending draft) and media into a throw-away database, dumps it, drops the source, restores into a second database, restores media, then verifies through Payload that the admin logs in with the original password, both locales and the draft are intact and the file exists.

**Real restore (Supabase):** 1) unset `CMS_ENABLED` (public pages keep serving static content); 2) create a **new** database/project, run `pg_restore` into it (use the pooler or direct URL from a machine that can reach it); 3) point `DATABASE_URL` at it; 4) redeploy; 5) verify login + a published page; 6) re-enable. Supabase Free does not include backups you can rely on — treat your own `pg_dump` as the only backup and check Supabase's current plan page before depending on anything else.

## 5. Security posture (summary; details in PAYLOAD_POC.md and DEPENDENCY_AUDIT.md)
Roles enforced server-side (not only in the UI); editors cannot publish, unpublish, restore, delete, change slugs/booking mapping, or manage users; drafts invisible to anonymous reads on every REST path tested (filters, sorts, versions, counts, search); no user/credential enumeration; GraphQL disabled; CSRF origin lock + CORS allow-list; `HttpOnly`/`Secure`/`SameSite=Lax` session cookie, 2 h sessions, lockout after 5 failures; admin/API responses noindex + `nosniff` + `X-Frame-Options: SAMEORIGIN`; uploads: images only, content-sniffed, ≤ 8 MB, alt text required, SVG rejected.
Known gaps: no rate limiting on login beyond per-account lockout (Vercel Firewall rules are available on all plans — add one for `/api/users/login` before production); password reset e-mail needs a real provider; no MFA (Payload supports it via plugins — evaluate for admin accounts).

## 7. Staging acceptance checklist (after provisioning)
1. `/admin` login as admin; create an editor; log in as editor in another browser.
2. Editor edits About (EN) → **Save Draft**; confirm no Publish button; confirm the public page is unchanged; use **Live Preview**.
3. Admin publishes; public EN page updates immediately; BS page unchanged; repeat for BS.
4. Same for Junior Suite; booking button still points to `roomtypeunkid=18019000000000000010`.
5. Upload an image (≤ 8 MB, with alt text); confirm it is served from `*.blob.vercel-storage.com`; try an SVG (must be refused).
6. Restart/redeploy; confirm content and media persist.
7. Take a `pg_dump`; run the restore procedure into a scratch database; verify.
8. Confirm `x-robots-tag: noindex` on `/`, `/admin`, `/api/*`; confirm staging URLs return the Vercel login wall when signed out.
9. Rotate `PAYLOAD_SECRET` once to prove the procedure.

## 8. Phase 2 additions to verify on staging
10. `npm run cms:seed` now also creates the Navigation, Footer and Home page globals (idempotent). Confirm the three globals open in `/admin/globals/*` and the public site is unchanged right after seeding (HTML equals the CMS-off site).
11. As **editor**: Navigation, Footer and Home page offer *Save Draft* and **no** Publish/Unpublish; menu structure and link fields are read-only. As **admin**: Publish is offered; publish a changed menu label in BS only and confirm EN is unchanged.
12. Create a page under *New pages* with different EN/BS addresses; confirm 404 while draft, staff preview works, publish makes it public at once, the sitemap lists it with correct alternates, and the language switcher goes to the other language's address.
13. Add an Offers/FAQ/CTA section with *DEMO / SAMPLE* ticked: label visible in preview, **publish refused** (staging only: `CMS_ALLOW_SAMPLE_PUBLISH` stays unset).
14. Remember: publishing is document-level (an admin publish also publishes the other language's pending draft) until per-language publishing (draft PR #17) is adopted.
