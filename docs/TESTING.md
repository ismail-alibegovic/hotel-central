# Quality gates and how to reproduce them

Requirements: Node 22, npm 10. Everything below runs from the repository root.

| Gate | Command | What it checks |
| --- | --- | --- |
| Install | `npm ci` | exact lockfile install |
| Lint | `npm run lint` | ESLint (`next/core-web-vitals`, `next/typescript`) |
| Types | `npm run typecheck` | `tsc --noEmit` |
| Build | `npm run build` | production build, 34 static pages (needs network for Google Fonts) |
| Smoke | `npm run test:e2e` | every EN/BS page and all 6 room pages at 390 / 768 / 1440 px: HTTP 200, one `<h1>`, correct `<html lang>`, no horizontal overflow, no broken images, no console errors or failed sub-requests; 404, root redirect, robots/sitemap, contact-API validation |
| Visual | `npm run test:visual` | above-the-fold screenshots of 11 pages × 3 widths against `tests/e2e/__screenshots__` (2 % pixel tolerance) |
| Payload integration | `npm run test:int` | CMS access control, drafts, locales, media, REST authorization (in-memory MongoDB, no cloud) |
| CMS end-to-end | `npm run test:cms-e2e` (extra arguments go to Playwright) | production build with `CMS_ENABLED=true` + Playwright: **HTML parity** (all 28 public pages equal a CMS-off build of the same code), CMS-vs-static pixel parity, admin UI (mobile/desktop), roles and drafts, per-language editing, link safety, SEO and sitemap, HTTP security, DB-outage build, bundle scans (see docs/architecture/CMS_CONTENT_MODEL.md and PAYLOAD_POC.md) |
| CMS visuals | `npm run test:cms-e2e -- --no-deps --project=visual-cms-mobile --project=visual-cms-tablet --project=visual-cms-desktop` | screenshots of CMS-only output in staff preview (offers/FAQ/CTA sections, a page created in the CMS, the home page with edited text and photograph) against `tests/cms-e2e/__screenshots__`; part of the normal `test:cms-e2e` run and of the CI `cms` job |
| Restore drill | `PATH="$(scripts/cms/install-mongo-tools.sh):$PATH" npm run cms:restore-drill` | mongodump → restore → verify through Payload |
| All static gates | `npm run check` | lint + typecheck + build |

The e2e commands start `next start` on port 3100 themselves, so run `npm run build` first.

## Browser setup
- Normal machine: `npx playwright install chromium`.
- Preinstalled Chromium (e.g. the cloud sandbox): `PW_CHROMIUM_PATH=/opt/pw-browsers/chromium npm run test:e2e`.

## Testing a deployment instead of a local build
`E2E_BASE_URL=https://hotel-central-pi.vercel.app npm run test:e2e` (read-only GETs plus one invalid contact POST that is rejected before any delivery). Do not point it at `hotelcentral.ba`.

## Visual baselines
Determinism measures: reduced motion forced (the site zeroes animation durations under `prefers-reduced-motion`), Playwright animation disabling, fixed locale and time zone, viewport-only captures (no parallax or lazy full-page drift), fonts awaited.

**The GitHub Actions runner is the source of truth.** Baselines were first generated in a different sandbox; on GitHub's runner 30/33 were byte-identical and 3 mobile images differed (`mobile/bs-contact`, `mobile/en-location`, `mobile/en-meetings-events`: hero paragraph/heading text metrics differ slightly, `bs-contact` even re-wraps one line; no layout, imagery or colour change — reviewed side by side with a pixel diff before acceptance). Baselines were then regenerated by the `Update visual baselines` workflow on the runner and the `visual` job has passed against them on repeated runs, so it is now **blocking**.

Consequence: run visual tests locally for a quick signal, but expect those 3 mobile images (and possibly others on other OSes) to differ locally; CI decides.

CMS-only baselines (`tests/cms-e2e/__screenshots__`, projects `visual-cms-*`) follow the same rules and are regenerated by the same workflow (it also runs the seeded CMS site with `--update-snapshots`).

### Changing baselines (design changes only)
1. Push a branch named `ci/update-baselines/<name>` containing your change. The `Update visual baselines` workflow regenerates all baselines on the CI runner and commits them to that branch (a `workflow_dispatch` trigger also exists but only works once the workflow is on the default branch).
2. Fetch the branch, **review every changed image** (side-by-side/pixel diff), and cherry-pick or fast-forward the baseline commit into your PR. Never regenerate to silence a failure you cannot explain.

## CI
Every job that needs a browser installs it through `scripts/ci/install-playwright.sh` (240 s per attempt, 3 attempts): `playwright install --with-deps` occasionally stalls for 10+ minutes on GitHub-hosted runners, which used to eat the whole job timeout and cancel a job whose tests had not started. Job timeouts leave room for a retried install.

`.github/workflows/ci.yml` runs on every PR and push to `main`: `quality` (lint, typecheck, build) → `smoke` and `visual` (both blocking). Node is `^24.22.1`, matching Payload 3.92's engine range (`^22.23.4 || >=24.22.1`). Failure reports are uploaded as artifacts. Enable branch protection on `main` requiring `quality` and `smoke` (repo owner action; not done here).

## Environment
`.env.example` lists variable names only. No variable is required to build or run the tests.
